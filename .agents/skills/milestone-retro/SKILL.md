# 마일스톤 회고 생성

> Codex `$milestone-retro`, Claude Code `/milestone-retro`. 인자로 마일스톤 슬러그를 줄 수 있고,
> 없으면 방금 닫은 마일스톤을 `docs/roadmap.md`와 git 기록에서 찾는다.

## 왜 이 스킬이 따로 있나

Trace에는 회고가 셋 있고, 담는 것이 다르다. 겹치지 않는다.

| 회고 | 누가 쓰나 | 단위 |
|---|---|---|
| `daily-retro` | 사용자 (인터뷰) | 하루 — 사용자가 직접 부를 때만 |
| **`milestone-retro`** | **사용자 (인터뷰)** | **마일스톤 — 실제 완결 단위** |
| MVP 완료 회고 (`trace-archive`) | 에이전트 (분석) | MVP 전체 |

MVP 완료 회고에는 **사용자 인터뷰가 없다.** 에이전트가 커밋과 문서를 분석해 쓴다.
사용자의 판단·감각이 들어가는 자리는 이 스킬과 `daily-retro`뿐이다.

"하루"는 세션 만료로 자주 잘려 회고 기준이 되기 어렵다(2026-07-30 확인). 마일스톤은
코드·실기기 QA·커밋이 모두 끝나는 지점이라 며칠에 걸쳐도 기준이 흔들리지 않는다.

## 트리거

**마일스톤을 닫을 때** — 실기기 QA 결과를 수용하고 `docs/roadmap.md`의 해당 마일스톤을
`[x]`로 바꾸는 시점. 에이전트가 먼저 제안한다(강제 아님, 사용자가 넘기면 넘긴다).

## Phase 1 — 데이터 수집 (생략 금지, 추측 금지)

마일스톤의 실제 산출물만 읽는다. 기억이나 추측으로 채우지 않는다.

```bash
git log {마일스톤 첫 커밋}^..{마지막 커밋} --format='%h %ad %s' --date=short
git diff {첫커밋}^..{마지막커밋} --stat
```

함께 읽을 것:

- 설계 문서 (`docs/superpowers/specs/`) — 무엇을 정했고 무엇을 범위 밖으로 뒀나
- 플랜 문서 (`docs/superpowers/plans/`) — Task별 진행, 리뷰에서 나온 지적
- 실기기 QA 체크리스트 (`docs/qa/`) — 통과·실패 항목과 사용자 판정
- 진행 원장 (`.git/sdd/progress.md`) — Task별 리뷰 결과

정리 결과(Phase 2 전에 내부적으로):

- 이 마일스톤에서 실제로 내린 의사결정 목록 (설계 문서·커밋 메시지·리뷰 반영에서 추출)
- 계획과 달라진 지점 (플랜에 없던 작업, 범위에서 뺀 것)
- QA에서 실패했거나 조건부로 넘어간 항목
- 리뷰가 잡아낸 결함 중 재발 가능성이 있는 것

## Phase 2 — 인터뷰 (1문 1답, 필수)

Phase 1의 **실제 데이터로만** 선택지를 만든다. "뭐가 어려웠나요?" 같은 빈 질문 금지 —
이미 답을 아는 상태에서 확인·보충만 받는다.

1. 추출한 의사결정을 번호 목록으로 제시 → 회고에 포함할 번호를 선택받는다 (예: `1,3,5`).
2. 이어서 질문 최대 3개. 각 질문은 A/B/C/직접입력 + **추천 항목·추천 이유** 포함:
   - Q1. 이 마일스톤에서 가장 어려웠던 점
   - Q2. 인사이트·교훈 — 다음에 같은 상황이면 어떻게 할지
   - Q3. 다음 마일스톤에서 다르게 할 것
3. **한 번에 하나씩** 묻는다. 응답을 받은 뒤 다음 질문으로. 답이 짧거나 "패스"도 허용.
4. 답변에 부연이나 곁가지가 섞여 있어도 **그 자리에서 실행하지 않는다** — 메모해두고 남은
   질문을 마친 뒤 종합한다 (`docs/agent-rules/skills.md` 다중 질문 규칙).

## Phase 3 — 회고 작성 (markdown)

```markdown
# {마일스톤 슬러그} 회고 — {한 줄 요약}

기간: {시작}~{종료} · 작업 종류: {새 기능|작은 기능|정비} · MVP{N} 마일스톤 {n}

## 무엇을 만들었나
(코드로 실제로 바뀐 것. 커밋 근거와 함께)

## 핵심 의사결정
(결정별: 상황 · 선택지 · 결정 · 왜 · 결과)

## 계획과 달라진 것
(플랜에 없던 작업, 범위에서 뺀 것, 그 이유)

## 어려웠던 점 / 교훈
(Phase 2 인터뷰 답변 반영)

## 다음 마일스톤에 넘기는 것
(미해결 항목 → `docs/backlog.md` 연결)
```

- 일기체로 — 딱딱하지 않게, 설명하듯.
- 핵심은 **의사결정의 "왜"**. 단순 기록이 아니라 인사이트 중심.
- 감정(막혔던 지점·뿌듯했던 점)도 담는다.
- 인포그래픽·HTML은 만들지 않는다. 마일스톤마다 만들면 무겁다 —
  필요하면 `daily-retro`나 MVP 완료 회고에서 한다.

## Phase 4 — 반복 문제 처리

회고에서 "반복될 수 있는 문제"가 나오면 반영을 제안한다 (A/B/C 선택지로).

| 문제 유형 | 반영 대상 |
|---|---|
| 재사용 가능한 기술적 교훈 | `ce-compound` → `docs/solutions/` |
| 워크플로 규칙 문제 | `docs/agent-rules/*.md` |
| 미룬 개선·기술부채 | `docs/backlog.md` |
| 반복 실수 (2회 이상) | `.githooks/` 등 기계적 차단 검토 |

원칙: **같은 문제가 두 번 나면 문서가 아니라 기계로 막는다.**

## Phase 5 — 저장 및 보고

- 저장 위치: `docs/retro/{YYMMDD}-{마일스톤슬러그}-retro.md`
- MVP가 끝나 `trace-archive`를 돌릴 때 `history/mvpN/`으로 함께 옮긴다.
- 저장 후 파일 경로와 Phase 4 제안 항목을 함께 보고한다.

## 출력 규칙

- 한국어. 코드 식별자·파일 경로는 원문 유지.
- 근거 없는 서술 금지 — 모든 주장은 커밋·문서·QA 결과 중 하나를 가리킬 수 있어야 한다.
- 길이는 마일스톤 규모에 비례. 작은 마일스톤에 억지로 분량을 채우지 않는다.
