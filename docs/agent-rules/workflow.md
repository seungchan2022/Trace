# Workflow Rules — MVP · 마일스톤 단위와 아카이빙

Trace의 작업 단위 정의와 "진행 → 완료 → 정리 → 학습" 흐름.
이 파일은 superpowers 워크플로 **위에 얹는 얇은 레이어**(단위 명명 + 아카이빙 + 학습)만
규정한다. spec/plan/구현/리뷰 자체는 superpowers가 수행하며, 이 파일이 그것을 대체하지 않는다.

## 작업 단위 (5계층)

| 단위 | 크기 | 산출물 / 위치 | 누가 만드나 |
|---|---|---|---|
| Step | TDD 한 바퀴 (실패→구현→통과) | plan 내부 체크박스 | superpowers |
| Task | 한 컴포넌트/한 책임 | plan 내부 섹션 | superpowers (`writing-plans`) |
| **마일스톤** | 기능 한 조각 — "뭘 만들었나"의 **추적 단위** | `docs/roadmap.md` 체크박스 | 이 워크플로 |
| **사이클** | superpowers 1바퀴(spec→plan→구현→커밋)가 도는 **실행 단위** = 마일스톤 **1개 이상**을 응집도 기준으로 묶음. 브랜치 1개, 며칠 분량 | `docs/superpowers/specs/` + `plans/` 각 1개 + 브랜치 1개 | superpowers |
| **MVP** | 사용자 가치를 완결하는 덩어리 = 마일스톤 여러 개의 묶음 | `docs/roadmap.md` 항목 → 완료 시 `history/<mvp>/` | 이 워크플로 |

- 마일스톤과 사이클은 **1:1이 아니다** (2026-07-07 분리 — 그 전엔 마일스톤=사이클이라 작은
  작업에도 문서 세트가 따로 나왔다). 작고 관련 있는 마일스톤들은 한 사이클로 묶고, 큰
  마일스톤은 사이클 하나를 통째로 쓴다. 묶음 제안은 에이전트가, 확정은 킥오프에서 사용자가.
  (전례: MVP10은 제스처 마일스톤 3개를 스펙 1개로 묶어 돌렸다.)
- 사이클 안에 brainstorm·리뷰·검증이 이미 들어 있으므로, **별도의 마일스톤 리뷰 장치를 두지 않는다.**
- **Task를 마일스톤으로 승격하지 않는다** (plan ↔ 마일스톤 계층이 중복돼 복잡해진다).

## 작업 종류 (새 기능 / 작은 기능 / 정비)

마일스톤 킥오프 때 종류를 **명시적으로 선언**하고 단계 표시줄에 적는다. 선언 없이 시작하지
않는다 — "규모·위험에 비례해 고른다"는 원칙이 선언 없이는 기본값 '전부'로 굳는다(MVP10 회고).
버그는 이 표가 아니라 아래 "버그 처리 경로"를 따른다.

| 단계 | 새 기능 | 작은 기능 | 정비 |
|---|---|---|---|
| 설계 문서 (`brainstorming`) | ○ | ○ | ✕ |
| 문서 리뷰 (`ce-doc-review`) | ○ | ✕ | ✕ |
| **대상 목록·분류** | — | — | **○ 필수** |
| 계획 문서 (`writing-plans`) | ○ | ○ | **위험 항목만** |
| TDD · Task별 코드리뷰 · 커밋 규칙 | ○ | ○ | ○ |
| 실기기 QA | ○ | ○ | 조건부 면제 |
| 최종 브랜치 리뷰 | ○ | ✕ | ✕ |

- **작은 기능 조건** (모두 충족 시): 열린 제품/아키텍처 결정이 없다 · 범위가 좁고 명확하다 ·
  새 레이어/외부 의존성이 없다. **하나라도 애매하면 새 기능.**
- **정비 조건**: 위 조건에 더해 **새 동작이 없다** — 린트 경고 정리, 이름 정리, 문서·로드맵
  보정, 의존성 갱신. 절차는 아래 "정비 작업 경로".
- 진행 중 위험이 드러나면 사용자에게 알리고 한 칸 무거운 쪽으로 올린다.
- 종류가 섞인 마일스톤들을 한 사이클로 묶지 않는다. 성격이 다르면 사이클을 나눈다 — 묶으면
  한쪽이 반드시 과잉이 된다(MVP17에서 `lint-cleanup`을 별도 마일스톤으로 뺀 판단).

## 세션 경계 (문서 세션 / 구현 세션)

한 사이클의 문서 작업(설계 → 리뷰 → 계획)만으로도 컨텍스트가 크다. **사이클 하나의 문서가
끝나면 세션을 닫는다.** 같은 세션에서 다음 사이클 문서까지 이어 쓰지 않는다.

- 새 세션은 `trace-init`으로 시작한다 — 무엇을 할 수 있는지 선택지를 받는다.
- 이유: 요청마다 누적 컨텍스트 전체가 다시 처리되므로, 찬 세션을 이어 쓰는 비용이
  새 세션 + `trace-init`보다 크다. 컨텍스트가 클수록 초점도 흐려진다.
- 문서 세션과 구현 세션의 모델 분리 정책은 사용자가 매 세션 직접 설정한다(규칙 대상 아님).

## 흐름: top-down (MVP를 먼저 세우고, 마일스톤을 채운다)

1. **MVP 킥오프** — 새 MVP는 "무엇을 만들지"부터 정한다.
   `superpowers:brainstorming`의 decompose 기능으로 MVP 범위를 마일스톤들로 쪼개고,
   `docs/roadmap.md`에 "MVP-N + 마일스톤 체크리스트"로 등록한다.
   목록은 **잠정** — 진행하며 조정 가능(빡빡하게 다 확정하지 않는다).
   - 킥오프 문서(`docs/superpowers/specs/<날짜>-mvpN-<슬러그>-kickoff-design.md`)에 아래 표를 넣는다.
     `trace-init`이 이 표를 읽어 "지금 할 수 있는 것"을 만든다.

     | 마일스톤 | 종류 | 앞 결과에 의존하나 |
     |---|---|---|
     | `<슬러그>` | 새 기능 / 작은 기능 / 정비 | 없음 / ⚠️ `<앞 마일스톤>`의 무엇 |

   - **의존 칸은 잠정이다.** 킥오프에서 아는 만큼만 적고, 실기기 QA 결과가 앞 마일스톤의
     처방을 뒤집으면 그 시점에 갱신한다 — MVP17 `run-idle-polish`의 의존은 킥오프에서
     예측된 것이 아니라 `history-tab` QA 실패로 드러났다.
   - **킥오프 문서는 사이클 설계를 겸하지 않는다.** MVP17 킥오프가 347줄로 부푼 것은 사이클
     1·4의 설계를 흡수해서였고, 그 결과 "설계 문서가 사이클당 하나"라는 규칙이 흐려졌다.
     사이클 설계는 2항에서 사이클마다 따로 쓴다.
   - ⚠️ **체크포인트(반복 실수 방지, 2026-07-01):** `docs/superpowers/specs/`에 design 문서를 쓰기
     **직전**, `docs/roadmap.md`에 이 MVP 항목이 이미 있는지 확인한다. 없으면 design 작성과 같은
     턴에 먼저 등록한다. MVP6·MVP7 모두 이 등록을 빼먹고 완료 시점에 소급 처리했다 — 브랜치명만으로는
     "이게 새 MVP 시작이다"를 감지할 수 없으므로, design 문서 작성이 가장 이르고 확실한 감지 지점이다.
2. **사이클 루프** — roadmap의 마일스톤을 사이클로 묶어 하나씩 (묶음·종류는 킥오프에서 확정).
   **어느 단계를 밟을지는 위 "작업 종류" 표를 따른다** — 아래 목록은 새 기능·작은 기능 기준이고,
   정비는 "정비 작업 경로", 버그는 "버그 처리 경로"로 간다.
   - `superpowers:brainstorming` → `docs/superpowers/specs/<날짜>-<슬러그>-design.md` (정비 ✕)
   - `superpowers:writing-plans` → `docs/superpowers/plans/<날짜>-<슬러그>.md` (정비는 위험 항목만)
   - `superpowers:executing-plans` → 구현·리뷰·검증·커밋 (feature 브랜치 1개)
   - 마일스톤이 끝날 때마다 `docs/roadmap.md`의 해당 마일스톤을 `[x]`로 갱신
     (사이클에 여러 개가 묶여 있으면 끝난 것부터 개별로 켠다).
   - 같은 시점에 `milestone-retro` 실행을 **제안**한다(강제 아님). 상세는 `docs/agent-rules/skills.md`.
   - `subagent-driven-development`로 실행 중이면, Task 리뷰가 끝나 완료 처리할 때마다
     **plan 파일 내부의 그 Task 체크박스도 같은 턴에 갱신**한다(roadmap 마일스톤 체크박스와는
     별도). MVP13 사이클 1·2 모두 실행 중엔 갱신하지 않고 아카이빙 시점에 소급 노트를 붙였다
     — 반복되면 매번 소급 처리 비용이 든다. (2026-07-15)
3. **MVP 완료** — roadmap의 그 MVP 마일스톤이 모두 `[x]`면:
   - **실기기 QA 체크리스트 작성 및 제출 (필수)** — UI·제스처·위치·권한 등 시뮬레이터로 검증 불가한 항목이 있는 MVP는 `docs/qa/YYYY-MM-DD-<feature>-device-checklist.md`를 작성하고 사용자에게 제시한다. 순수 로직·docs·리팩터링만 포함된 MVP는 면제. 상세 템플릿은 `docs/agent-rules/testing.md`의 "Real-Device Verification" 절 참고.
   - `trace-archive` 공용 스킬 — spec+plan을 `history/<mvp>/`로 아카이빙 (Codex `$trace-archive`, Claude Code `/trace-archive`).
   - `trace-study` 공용 스킬 — 학습 정리 (선택, 권장; Codex `$trace-study`, Claude Code `/trace-study`).

> MVP는 "나중에 묶는 라벨"이 아니라 **"먼저 세우는 우산"**이다. 시작 시점에 묶음 기준이
> 정해지므로, 마일스톤을 다 만든 뒤 "이걸 어느 MVP로 묶지?"를 고민하는 사후 분류 문제가 없다.

## 리뷰·분석을 끼우는 지점 (권장)

워크플로 사이에 리뷰/분석을 넣어 결함을 일찍 잡는다. **도구는 새로 만들지 않는다** — 이미 설치된
superpowers / compound-engineering을 해당 지점에서 호출한다. 강제(훅)는 아니며, 변경 규모·위험에
비례해 고른다(매번 전부 거치는 게 아니다).

| 워크플로 지점 | 권장 호출 (실존 확인 2026-07-30) | 무엇을 잡나 |
|---|---|---|
| MVP 킥오프(로드맵·마일스톤 분해) 직후 | `ce-doc-review` | 기획·로드맵의 구조 결함 (구현 전이 수정비용 최저) |
| 사이클 spec 완료 시 (새 기능만) | `ce-doc-review` | 설계 구멍·전제 오류 |
| 기술 결정 갈림길 | `superpowers:brainstorming`(2~3안 비교) | 대안 비교 없이 한 길로 가는 것 |
| 아키텍처/외부 조사 필요 | `context7`(라이브러리·API 문서) · `WebSearch`로 근거 수집 → 모은 근거로 `advisor` 검토 | 구조 이해 부족·바퀴 재발명 |
| **구현 후 · 커밋 전** (가장 중요) | `superpowers:requesting-code-review` + `/code-review` | 코드 결함·회귀 |
| 막힐 때(버그·재현 안 됨) | `superpowers:systematic-debugging` | 추측 기반 수정 |

- **조사 없이 `advisor`를 부르지 않는다** — 근거가 없으면 검토도 추측이 된다. `advisor`를 언제
  부르는지의 규칙은 `docs/agent-rules/dual-tool.md`에 있다(이 파일에 옮겨 적지 않는다).
- **적대적 검토는 별도 호출이 아니다.** `ce-doc-review`가 문서 내용을 보고 필요하면
  adversarial 검토자를 내부에서 띄운다(항상 오는 coherence·feasibility 2명 + 조건부 5명, 최대 7명).
  이전 표에 있던 `ce-adversarial-reviewer`·`ce-adversarial-document-reviewer`·
  `ce-architecture-strategist`·`ce-best-practices-researcher`·`ce-web-researcher`는
  설치된 compound-engineering 3.19.0에 **존재하지 않는 이름**이라 2026-07-30에 제거했다
  (경위: `docs/workflow-audit.md` §5-1).

- **커밋 전 코드리뷰**는 빠뜨리지 않는다(통증이 가장 큰 지점). 지금은 규칙으로 강하게 권장하고,
  반복적으로 빠지면 그때 `.githooks`/훅으로 하드 강제를 검토한다.
- 하드 강제를 전면 도입하지 않는 이유: Claude Code엔 "단계(Step)" 이벤트가 없어 **중간 단계의
  무조건 강제는 구조적으로 불가**하고(커밋 등 도구 시점만 훅으로 막을 수 있음), 솔로 개발에 과한
  자동 게이트는 무한루프·거짓양성 마찰을 부른다. 통증이 실측되면 그 지점만 최소로 막는다.
- **리뷰 서브에이전트가 인프라 오류(connection closed, stalled 등)로 2회 연속 실패하면**,
  3번째 시도부터는 같은 프롬프트를 그대로 재시도하지 않는다 — 조사 범위와 보고 길이를 좁힌
  더 가벼운 프롬프트로 다시 디스패치한다. MVP13 사이클 2 Task 3 리뷰에서 3연속 인프라 실패
  후 이 방식으로 4번째 시도가 성공했다. (2026-07-15)

## 정비 작업 경로 (목록·분류는 유지, 상세 계획은 위험 항목만)

새 동작도 열린 제품 결정도 없는 작업 — 린트 정리, 이름 정리, 문서·로드맵 보정, 의존성 갱신.
설계 문서와 문서 리뷰를 생략하되 **분류 단계는 생략하지 않는다.** (2026-07-30, MVP17
`lint-cleanup` 실측에서 정립. 근거: `docs/workflow-audit.md`)

1. **대상 목록·분류 (생략 금지)** — 손댈 대상을 **실측해** 목록으로 만들고 갈래별 처분을 정한다.
   분량은 표 하나면 된다. **이 단계가 위험을 잡는다** — `lint-cleanup`에서 린트 경고 44건을
   분류하다 5건이 `Codable` 저장 키임이 드러났다(그대로 개명하면 사용자 기기의 러닝 기록이
   해독 불가가 되는 경로였다. 함정 원문: `docs/solutions/conventions/codable-property-rename-breaks-stored-blobs.md`).
2. **상세 계획은 위험 갈래에만** — 분류에서 위험으로 표시된 갈래만 `writing-plans`로 Task별
   계획을 쓴다. 나머지 갈래는 계획 문서 없이 바로 구현한다.
3. **승격** — 진행 중 새 동작이나 제품 결정이 필요해지면 멈추고 사용자와 상의한다. 필요 시
   작은 기능으로 올린다.
4. **유지되는 것**: TDD, 커밋 전 코드리뷰 1회, 커밋 규칙, `ce-compound` 판단(`skills.md`).
5. **실기기 QA 면제 조건**: 새 동작이 없으므로 UI·제스처·위치·권한 검증이 불필요하다. 단
   **면제되는 부분이 자동 검증으로 덮여야 면제가 성립한다.** `lint-cleanup`은 사용자 데이터에
   닿는 유일한 부분(저장 포맷)을 새 테스트로 덮은 뒤에 면제를 적용했다. 시뮬레이터 육안 확인만으로
   충분한 부분은 그 확인을 Step에 명시한다.

## 버그 처리 경로 (전체 사이클을 태우지 않는다)

버그는 "코드가 이미 정해진 스펙과 다르게 동작하는 것"이라 열린 제품 질문이 없다 —
새 사이클(brainstorm→spec→plan)을 시작하지 않는다. (2026-07-08, MVP11 줌아웃 버그에서 정립)

1. **분류** — 실기기 QA·실사용 보고가 들어오면 먼저 가른다: **진짜 고장**(스펙대로 안 동작,
   현재 MVP의 QA 통과를 막음)이면 지금 고치고, **의도 불일치·개선**이면 `docs/backlog.md`에
   기록 후 다음 마일스톤 후보로 미룬다. 분류 기준의 원문은 `docs/agent-rules/testing.md`의
   Real-Device Verification 절. 분류를 확정하기 전에 `advisor` 도구로 검토를 거치고, 결론을
   대화에서 한 줄로 먼저 선언한다(예: "진짜 고장 → 지금 고침", "의도 불일치/개선 → 백로그
   등록"). (2026-07-13)
2. **수정** — "지금 고침"이면 같은 브랜치에서 `superpowers:systematic-debugging`으로 직행:
   가설 → 계측 → 최소 수정 → **원인 소멸 검증**(증상이 아니라 원인이 사라졌는지) →
   테스트 그린 → 커밋. 스펙·플랜 문서는 만들지 않는다. 원인을 확정하기 전에 `advisor` 도구로
   검토를 거친다. 시도 횟수는 에이전트가 스스로 추적한다(사용자가 지켜보다 알려주는 방식이
   아니다) — 가설 하나를 시도하고 실패할 때마다 "시도 N/3 실패: 이유"를 한 줄 남기고 다음
   가설로 넘어간다. (2026-07-13)
3. **승격 — 예외 두 가지만**:
   - 수정이 **제품 결정을 바꾸면**(UI 구조 교체, 데이터 의미 변경 등) 멈추고 사용자와 상의.
     필요 시 스펙·`project-decisions.md` 갱신.
   - **같은 버그에 3회 실패하면**(위 시도 카운트 기준) 4번째 시도 대신: 시도 코드를 되돌리고
     인수인계 문서(확정 사실 / 막다른 시도와 실패 이유 / 금지 사항 / 미해결 질문)를 남긴 뒤
     세션을 리셋한다. 사용자 확인을 기다리지 않고 바로 진행한다. 전례:
     `history/mvp11/2026-07-08-map-zoom-during-alert-bugfix.md`,
     판단 근거: `docs/solutions/workflow-issues/session-reset-after-repeated-fix-failures.md`.

- **기각 기록 원칙**: 가설·시도를 기각할 때 "무엇을"만이 아니라 **"어디에/어떻게"**(적용
  위치·계층·조건)까지 기록한다. 조건 없는 기각은 정답을 오답 처리할 수 있다 — MVP11에서
  올바른 수정이 적용 계층 문제로 기각돼 있었다
  (`docs/solutions/design-patterns/swiftui-keyboard-avoidance-shrinks-representable.md`).

## 단계 표시 (가시화)

사이클 작업 중에는 응답에 현재 위치를 한 줄로 표시해 "어디까지 탔는지" 보이게 한다
(frank의 `Step N/9` 경량판 — 강제가 아니라 관례). 종류 선언과 리뷰 지점을 거쳤는지/건너뛰었는지도 이 표시로 드러난다.

```
[지금: MVP{N} · 사이클 '{슬러그}' ({새 기능|작은 기능|정비}) — {기획 | 기획 리뷰 | 목록·분류 | 플랜 | 구현 | 커밋 전 코드리뷰}]
```

- 어떤 스킬이 방금 발동했는지도 함께 적는다(예: `구현 · TDD 3단계`, `기획 · brainstorming 인터뷰`).
  흔적을 남기지 않는 단계(설계 대화, 빌드 실행, 서브에이전트 디스패치)가 이 한 줄로만 보인다.

- `docs/roadmap.md`가 "어느 MVP·마일스톤"인지의 출처, 이 한 줄이 "그 사이클 안 어디인지"를 보여준다.

## 새 MVP를 정하는 기준

- 하나의 사용자 시나리오/가치를 완결하는가 (예: "러닝 코스 계획").
- 마일스톤 **2~5개** 규모 (그보다 커지면 MVP를 쪼갠다).
- `docs/backlog.md` 항목은 **마일스톤 후보**다 — 묶어서 새 MVP를 구성하거나, 기존 MVP의
  마일스톤으로 편입한다.

## 아카이빙 (실행 절차: `.agents/skills/trace-archive/SKILL.md`)

- **트리거**: MVP의 모든 마일스톤 완료.
- **동작**: 완료된 spec+plan을 `git mv`로 `history/mvpN/`(예: `history/mvp1/`)로 이동 + 완료 회고 1편 +
  `history/INDEX.md` 갱신 + `docs/roadmap.md` done 처리.
- `docs/superpowers/specs|plans/` 루트에는 **진행 중 마일스톤 문서만** 남긴다.
- **엣지케이스(소급 정리)**: 코드는 완료됐는데 plan 체크박스가 비어 있으면, 체크박스를 전부
  복원하지 말고 plan 상단에 "완료(소급 확인) — 근거 커밋" 한 줄 노트 + done 표시 후 아카이빙한다.

## 학습 (실행 절차: `.agents/skills/trace-study/SKILL.md`)

- 완료된 MVP를 "흐름 + 개념" 산문과 셀프 퀴즈로 `history/<mvp>/concepts.md`에 정리한다.
- 목적: "어떻게 만들었나"를 면접/실무에서 **자기 언어로 설명**할 수 있게 체화하는 것.
