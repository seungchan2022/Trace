이 앱은 어떤 방향으로 짜여 있나

Trace의 설계에는 일관된 방향이 하나 있다. 바로 바깥 세상에 닿는 것을 전부 갈아끼울 수 있게 만든 것이다.

바깥 세상이란 GPS, 애플 지도 서버, 디스크, 스피커처럼 앱이 통제할 수 없는 것들이다. 이것들은 느리고, 실패하고, 결과가 매번 다르다. 그래서 Trace는 이것들을 코드 곳곳에 흩뿌리지 않고 한 겹 뒤에 숨긴 다음, 통째로 가짜와 바꿔 끼울 수 있게 해뒀다.

이 방향 하나에서 나머지가 줄줄이 따라 나온다. 앱을 켤 때 진짜/가짜 갈림길이 있는 것도, 만드는 자리를 한 군데로 모은 것도, 폴더를 여섯 개로 나눈 것도 전부 이것 때문이다. 이 덩어리는 그 방향을 이해하는 것이 목표다.

그리고 이걸 알면 다음 기능을 어디에 놓을지도 따라온다. "달리는 중에 심박수를 보여주자"를 하기로 했을 때, 심박수 읽어오는 코드를 어느 폴더에 두고 누가 그걸 알아도 되는지를 규칙에 맞춰 스스로 정할 수 있게 된다.

이 앱에 뭐가 있나

이 파트를 끝내면

이 앱에 뭐가 있는지 이름과 역할을 댈 수 있다.

이 파트 한 줄 Trace는 코스를 그리고, 그 코스를 달리고, 달린 걸 다시 본다. 화면 셋 뒤에 일하는 것들이 붙어 있고, 달리기의 주인공은 RunSession이다.

구조를 보기 전에 등장인물부터 알아야 한다. 이름을 모르는 것의 역할을 설명해봐야 안 들어오기 때문이다. 여기서는 "뭐가 있고 각자 뭘 하는지"만 본다.

기록 화면이 읽는 곳은 러닝 화면이 쓰는 그 저장소와 같은 것이다. 그림에서는 선이 가로지르지 않게 따로 그렸다.

코스 쪽

지도에 손가락으로 선을 그으면 그게 실제 도로를 따라가는 경로로 바뀌어야 한다. 비뚤배뚤 그은 선을 그대로 쓰면 건물을 뚫고 지나가니까. 그 일을 하는 것이 아래 셋 중 첫 번째다.

MapKitCoursePlanningService

CourseEditSession
만들어진 경로 조각들을 이어붙이고, 되돌리고, 지운다. 코스 하나를 편집하는 동안의 상태를 통째로 들고 있다.
SwiftDataCourseRepository
이름 붙여 저장한 코스를 디스크에 넣고 꺼내온다. Repository는 "저장소"라는 뜻으로, 저장·조회만 하는 것에 붙이는 흔한 이름이다.

앱이 켜지는 순서

이 파트를 끝내면

새 부품을 언제 만들고 언제 일을 시작시킬지 정할 수 있다.

이 파트 한 줄 앱이 켜지면 등장인물을 전부 만들고, 그중 버튼이 없어서 스스로 알아채야 하는 둘만 미리 신청을 걸어둔 뒤, 화면을 띄운다.

먼저 하나 밝혀둘 것이 있다. 여기 나오는 건 전부 코드 안에서만 일어나는 일이라 화면에서는 아무것도 보이지 않는다. 아이콘을 누르고 첫 화면이 뜨기까지의 짧은 순간이다.

①
앱이 켜진다. 아이폰이 TraceApp의 시작 부분을 딱 한 번 실행한다. 화면은 아직 없다. 여기서 하는 일은 화면을 그리는 게 아니라 화면이 쓸 것들을 미리 만들어두는 것이다.
②
진짜로 돌지, 테스트용으로 돌지 정한다. 앱을 켤 때 -traceUITesting이라는 꼬리표가 붙어 있으면 테스트용으로 간다. 평소에 아이콘을 눌러 켜면 안 붙어 있다. 갈림길은 여기 한 곳뿐이고, 이후 코드는 자기가 어느 쪽인지 모른다.
③
파트 0의 등장인물을 전부 만든다. 길찾기, 위치, 저장소 둘, RunSession, 잠금화면 담당, 소리 담당까지 DependencyContainer 안에서 한 번에 만들어진다. 여기가 앱의 조립 지점이다.
④
잠금화면 담당과 소리 담당에게 "지켜봐"라고 시킨다. 이 둘만 그렇게 한다. 나머지는 안 시킨다. 아래에서 이유만 짚는다.
⑤
잠금화면 버튼이 두드릴 문을 열어둔다. 잠금화면 위젯의 "포인트 찍기" 버튼이 눌렸을 때 실행될 것을 미리 등록한다.
⑥
화면을 띄운다. 여기서 처음 화면이 나온다. ③에서 만든 것을 통째로 넘긴다. 탭 셋이 동시에 살아 있고, 안 보이는 쪽은 투명도를 0으로 만들어 숨긴다.
⑤의 잠금화면 버튼은 7번 덩어리, ⑥의 탭 처리 방식은 UI 쪽이라 학습 범위 밖이다. (탭을 치우면 SwiftUI가 그 화면을 없애버려서, 저장 전의 작업 중인 것 — 그리던 코스, 보고 있던 지도 위치 — 이 날아간다. 그래서 안 치우고 숨기기만 한다.)

④에서 왜 둘만인가

달리는 동안 돌아가는 기능은 훨씬 많다. 거리 계산, 일시정지, 목표 진행, 신호 약함 감지, 기록 저장까지 아홉 가지쯤 된다. 그런데 앱 켤 때 "지켜봐"라고 시키는 건 딱 둘이다.

갈리는 기준은 하나다. 불러주는 사람이 있느냐.

거리 계산이든 일시정지든 대부분은 RunSession이 하고, 달리기 화면이 직접 부린다. "시작"을 누르면 화면이 "시작해"라고 말하고, "일시정지"를 누르면 "멈춰"라고 말한다. 불러줄 때만 움직이니 미리 시켜둘 게 없다.

잠금화면과 소리는 버튼이 없다. "지금 위젯 띄워" 버튼도 "지금 말해" 버튼도 없다. 1km를 지나는 순간 사용자는 그냥 뛰고 있을 뿐이다. 불러주는 사람이 없으니 스스로 알아채는 수밖에 없고, 알아채려면 미리 "이 값이 바뀌면 나를 깨워줘"라고 신청해둬야 한다.

주의할 게 하나 있다. 앱 켤 때 시작되는 건 "신청"까지고, 일은 아직 안 한다. 잠금화면 담당은 켜자마자 지켜보기만 하고 위젯은 안 띄운다. 달리기가 시작돼야 띄운다. RunSession도 앱 켤 때 이미 만들어져 있지만 가만히 있다가 화면이 부를 때 움직인다. 만들어지는 것과 일하는 것은 다른 시점이다.

"지켜본다"가 코드로 정확히 어떻게 동작하는지(startObserving은 이 프로젝트가 직접 지은 이름이고, 그 안에서 Swift의 withObservationTracking을 쓴다)는 6번(소리)·7번(잠금화면) 덩어리에서 다룬다. 여기서는 "버튼 없는 기능은 스스로 지켜본다"까지만.

②의 테스트용 갈림길

💡 UI 테스트는 왜 앱 코드에 갈림길이 필요한가?

먼저 UI 테스트에는 사람이 없다. 사람이 시뮬레이터를 보는 게 아니라 프로그램이 앱을 대신 켜고, 대신 버튼을 누르고, 화면에 뭐가 떴는지 스스로 확인한다. 명령어 하나 치면 알아서 돌고 "통과/실패"만 뱉는다.

그리고 그 프로그램은 앱을 "다른 프로그램"으로 띄운다. 서로 다른 프로세스라 앱 안에 손을 넣을 수가 없다. 밖에서 할 수 있는 건 셋뿐이다 — 꼬리표를 붙여서 켜기, 화면 두드리기, 화면에 뭐가 보이는지 읽기.

그래서 -traceUITesting이라는 꼬리표가 유일한 통로고, 앱이 스스로 그걸 읽고 갈아끼우는 수밖에 없다. 반면 단위 테스트는 같은 프로그램 안에서 돌아서 꼬리표 없이 가짜를 직접 넣는다. 실제로 RunSessionTests는 자기가 만든 가짜 위치 스트림과 가짜 저장소를 그대로 넘긴다. 그래서 앱 코드에 갈림길이 있고 단위 테스트에는 없다.

갈아끼우는 건 넷이다. 길찾기는 진짜로 하면 애플 서버에 요청이 가서 느리고, 인터넷이 없으면 실패하고, 응답이 매번 조금씩 다르다. 위치는 서울시청으로 고정한다 — 안 그러면 시뮬레이터 설정에 따라 화면이 달라져서 같은 테스트가 어제는 통과하고 오늘은 실패한다. 저장소 둘은 메모리에만 쓴다. 안 그러면 테스트가 실제로 저장해둔 코스를 건드린다. 소리는 아무것도 안 하는 걸로 바꾼다.

공통점은 "매번 결과가 같아야 한다"이다. 사람이 없으니 "어? 오늘은 위치가 다르네" 하고 넘어가 줄 사람도 없다. 바깥 세상에 닿는 것은 전부 결과가 흔들리므로 그것들만 골라서 갈아끼운다. 갈아끼울 수 있게 만들어놓은 구조가 파트 3의 주제다.

덧붙여 이 가짜 세상은 시뮬레이터에서 손으로 확인할 때도 쓴다. 맥북 앞에 앉아 있으면 GPS가 안 움직여서 달리기 화면이 0km에 멈춰 있는데, 가짜 위치가 0.5초마다 북쪽으로 1.5m씩 옮겨준다. 초속 3m, 킬로미터당 5분 33초 — 실제 달리기 페이스다.

@main
struct TraceApp: App {                                  // ①
    private let container: DependencyContainer

    init() {
        if ProcessInfo.processInfo.arguments             // ②
             .contains("-traceUITesting") {
            container = .uiTesting()
        } else {
            container = .live()                          // ③
        }
        container.runActivityController.startObserving() // ④
        container.runAudioCoach.startObserving()         // ④

        MarkRunWaypointIntentBridge.handler = { ... }     // ⑤
    }

    var body: some Scene {
        WindowGroup {
            RootView(container: container)               // ⑥
        }
    }
}

레이어 6개와 의존 방향

이 파트를 끝내면

새 코드를 어느 폴더에 놓을지 정할 수 있다.

이 파트 한 줄 폴더는 6개고 화살표는 전부 Domain을 향한다. 핵심은 Domain에 엔티티만 있는 게 아니라 인터페이스(프로토콜)도 같이 있다는 것 — 그래야 가장 바깥 Infrastructure의 화살표가 안쪽으로 뒤집힌다. 다만 유스케이스 층은 아직 없다(아래 마지막 절).

💡 인터페이스가 왜 하필 Domain에 있나?

화살표를 뒤집기 위해서다. 엔티티만 있으면 Infrastructure가 Domain을 향할 이유가 없다 — 그냥 옆에 있는 남남이 된다.

그런데 인터페이스가 Domain에 있으면, Domain이 "위치를 알려주는 것은 이런 모양이어야 한다"고 내걸고 Infrastructure가 그 모양에 자기를 맞춘다. 가장 바깥에 있는 층이 가장 안쪽을 향하게 되는 것 — 의존성 역전이다.

결과가 이것이다. RunSession은 RunLocationStreamProtocol이라는 약속만 안다. 그 자리에 진짜 GPS가 꽂혔는지, 0.5초마다 북쪽으로 움직이는 가짜가 꽂혔는지 알 방법이 없다.

화살표가 전부 한 방향이다

화살표 방향이 곧 "누가 누구를 아는가"다. 화면은 진행 상태를 알고, 진행 상태는 개념을 안다. 그런데 Domain에서 나가는 화살표는 하나도 없다. Domain은 자기 바깥에 뭐가 있는지 전혀 모른다.

재밌는 건 Infrastructure다. 바깥 세상을 다루는 가장 "낮은" 층인데 화살표가 위로 향한다. Domain이 "위치를 알려주는 것은 이런 모양이어야 한다"고 약속을 내걸면, Infrastructure가 그 약속에 맞춰 자기를 만든다. Domain이 Infrastructure를 부르는 게 아니라 반대다.

말이 아니라 실측이다

이건 주장이 아니라 세어보면 나온다. 각 폴더가 무엇을 import 하는지가 증거다.

폴더무엇을 가져다 쓰나
Domain Foundation 25 · ActivityKit 1
바깥 프레임워크 0건
Application Foundation 6 · Observation 4
바깥 프레임워크 0건

Domain 25개 중 24개가 Foundation 한 줄뿐이다. 나머지 한 개(RunActivityAttributes)만 ActivityKit을 더 쓰는데, 잠금화면 위젯 규격을 애플이 그렇게 요구해서 생긴 예외다. 코드 주석에도 의도가 그대로 적혀 있다 — "음성 안내 포트 — Domain은 AVFoundation을 모른다."

이 구조로 얻는 것 — 받은 대가와 안 쓴 보험

이미 받은 대가는 테스트다. 파트 1의 ② 갈림길이 가능한 이유가 이것이다. 테스트용으로 바꿀 때 Infrastructure의 구현만 가짜로 갈아끼우면 되고, Domain과 Application은 한 줄도 안 바뀐다. 단위 테스트에서 목을 직접 넣는 것도 같은 구조 덕이다.

아직 안 쓴 보험은 제공자 교체다. project-decisions.md에 이렇게 적혀 있다 — "지도 표시나 길찾기 제공자를 미리 갈아치우지 말 것. 나중에 바꾸게 되면 그건 뷰 레이어 국소 재작성이지 기능 재구축이 아니다." 애플 지도 대신 다른 길찾기를 쓰게 될 경우를 대비해 걸어둔 것이고, 아직 쓸 일은 없었다.

세 번째는 모듈 분리다. 지금은 한 덩어리지만 나중에 SPM으로 쪼갤 때 경계가 이미 그어져 있다. 이것도 결정으로 남아 있다 — "모듈 분리(SPM) 없음 — 추후 과제 유지."

그런데 이걸 "클린 아키텍처"라고 불러도 되나

엄밀히는 아니다. 정통 클린 아키텍처의 두 번째 층인 유스케이스가 없다. 코드 전체에서 UseCase라는 이름은 0건이고, Application의 6개는 유스케이스가 아니라 세션·오케스트레이터다.

💡 유스케이스와 세션은 뭐가 다른가?

유스케이스는 단발성이다. "코스를 저장한다" 같은 동작 하나를 받아서 실행하고 끝난다. 상태를 안 들고 있다.

세션은 시간을 들고 있다. RunSession은 달리기가 시작될 때 생겨서 끝날 때까지 계속 살아 있으면서 거리·시간·일시정지를 누적한다. "시작한다 / 멈춘다 / 재개한다 / 끝낸다"가 전부 같은 물건 위에서 일어난다.

달리기는 본질적으로 긴 작업이라 단발성 유스케이스로 쪼개기 어렵다. 그래서 세션 쪽을 골랐다고 보는 게 맞다.

그리고 이건 규칙을 어긴 게 아니라, 규칙이 미리 열어둔 문이다. docs/agent-rules/architecture.md에 "Application owns use cases"라고 적혀 있지만, 같은 문서가 바로 예외도 적어놨다 — "간단한 MVP 흐름에서는 ViewModel이 도메인 프로토콜을 직접 불러도 된다. 유스케이스가 제 값을 할 때까지."

표현도 정확히 그렇게 되어 있다. project-decisions.md는 "Clean Architecture boundaries"라고 쓴다 — 클린 아키텍처 그 자체가 아니라 그 경계선을 쓴다는 뜻이다. 실제 구현 이력 문서들은 이 구조를 포트-어댑터라고 부른다.

더 정확히 말하면 층이 없는 게 아니라 모양이 다르다. 클린 아키텍처에서 유스케이스 층의 책임은 "애플리케이션 고유 규칙"인데, Application이 그걸 담고 있다 — 달리기가 어떻게 진행되는지, 언제 멈춤으로 치는지. 책임은 채워져 있고 클래스 모양만 세션이다.

다만 두 경우를 나눠 봐야 한다. 달리기는 의도한 변형이다 — 긴 작업이라 단발성으로 쪼개면 오히려 이상해진다. 반면 코스 저장 같은 단발 동작은 "아직 안 만든 것"이다. CoursePlannerPageViewModel이 저장소를 직접 부른다(368행 저장 · 377행 조회 · 419행 삭제). 문서가 남긴 문이 이 경우다.

정리 의존성 역전과 Domain 중심은 클린 아키텍처 그대로다. 유스케이스 층의 책임은 세션 객체가 맡고 있다 — 층이 빈 게 아니라 모양이 다르다. 문서가 쓰는 표현은 포트-어댑터 + MVVM, 그리고 클린 아키텍처 "경계"다.
새 물건은 어디에? "달리는 중에 심박수를 보여주자"라면 — 심박수라는 개념과 약속은 Domain, 애플워치에서 실제로 읽어오는 코드는 Infrastructure, 달리는 동안의 진행 상태는 Application(RunSession 곁), 보여주는 건 Pages. 그리고 만드는 자리는 컨테이너 한 곳.

파트 3 / 6

약속 읽는 법 — 무엇을 보장하고 무엇을 안 정했나

이 파트를 끝내면

새 프로토콜의 throws·async·반환값을 정할 수 있다. 남의 프로토콜은 세 줄만 보고 계약을 읽을 수 있다.

이 파트 한 줄 파트 2가 약속이 어디 있나였다면, 여기는 약속에 뭐라고 적혀 있나다. throws가 있냐 없냐 같은 세 글자가 화면 설계를 정한다.

이 파트는 앞으로 남은 8덩어리를 읽을 도구다. 목표 깊이 C가 "무엇을 받아 무엇을 보장하는가"인데, 그게 프로토콜에 문자 그대로 적혀 있다. 구현을 다 읽지 않아도 계약을 알 수 있다.

세 줄에 계약이 다 들어 있다

@MainActor
protocol LocationServiceProtocol {
    func currentLocation() async throws -> CourseCoordinate
}

한 줄을 넷으로 쪼개 읽는다. currentLocation()은 아무것도 안 받는다. async는 시간이 걸릴 수 있으니 기다리라는 뜻이다. throws는 실패할 수 있다이고, -> CourseCoordinate는 성공하면 좌표를 준다이다.

💡 "실패할 수 있다"는 "실패해야 한다"가 아니다

테스트용 가짜는 서울시청 좌표를 즉시 돌려주고 절대 실패하지 않는다. 그래도 약속 위반이 아니다 — throws는 허가지 의무가 아니다.

반대로 부르는 쪽은 실패를 반드시 다뤄야 한다. Swift가 강제해서, try 없이 부르면 아예 컴파일이 안 된다.

이 비대칭이 갈아끼우기를 가능하게 한다. 구현체는 자유롭고 호출자는 의무다. 실패 종류는 따로 정의돼 있다 — LocationError에 denied(권한 거부)와 unavailable(신호 없음) 둘.

일부러 안 정한 것이 더 중요하다. 약속에 없는 것들 — 어떻게 위치를 얻는지, 얼마나 걸리는지, 정확도가 얼만지, 재시도를 하는지. 빠뜨린 게 아니라 의도다. 하나라도 적는 순간 갈아끼울 폭이 줄어든다.

throws 세 글자가 화면을 바꾼다

protocol CourseRepositoryProtocol: Sendable {
    func saveCourse(_ course: SavedCourse) async throws
    func fetchCourses() async -> [SavedCourse]        // throws 없음
    func deleteCourse(id: UUID) async throws
}

조회만 throws가 없다. 저장과 삭제는 실패할 수 있는데 조회는 아니다. 즉 "조회는 절대 실패하지 않는다"를 약속한 것이고, 그래서 코스 목록 화면은 "불러오기 실패" 상태를 만들 필요가 없다.

💡 조회가 실패할 수 없다고 약속할 수 있는 이유

에러가 안 나서가 아니라, 앞 단계에서 이미 처리했기 때문이다.

앱이 켜질 때 저장소를 여는데, 못 열면 손상 파일을 백업으로 옮기고 새 빈 저장소를 만들어서라도 앱을 띄운다(스펙 §2 — "어떤 경우에도 앱은 뜬다, 런치 크래시 금지"). 그 순간 코스는 진짜로 0개다. 그러니 나중에 빈 배열이 나오는 건 "불러오기가 실패한 것"이 아니라 "불러올 게 없는 것"이고, 빈 배열이 정직한 답이다.

개별 행이 깨진 경우도 compactMap으로 그 줄만 버리고 나머지를 준다. 한 줄 때문에 멀쩡한 열아홉 개를 못 보면 안 되기 때문이고, 그 행을 지우지도 않는다 — 사용자 자산이라서.

저장·삭제는 반대다. 사용자가 "지웠다"고 믿는데 안 지워지면 큰일이라, 실패를 반드시 알린다. 규칙은 이렇다 — 뭔가를 바꾸려 한 동작은 실패를 알리고, 그냥 보는 동작은 조용히 빈 값을 준다.

세 번째는 정반대 모양이다

func announce(_ text: String, pace: AnnouncementPace, kind: AnnouncementKind)
// throws 없음 · async 없음 · 반환값 없음

주석이 이유를 말한다 — "발화는 fire-and-forget: 호출자는 완료를 기다리지 않고, 직렬화(큐)는 구현체 책임이다." 말해달라고 하고 잊는다. 성공했는지도 안 알려준다. 달리는 중에 "음성 재생 실패" 알림을 띄울 수도 없고 띄울 이유도 없기 때문이다. 실제로 통화 중이라 실패하면 그 발화를 그냥 건너뛴다(재시도 없음 — 플랜 결정).

정리 약속의 모양이 용도를 따라간다. 위치는 실패를 알려야 하고, 조회는 절대 실패하지 않겠다고 약속하고, 음성은 성공 여부를 알릴 필요가 없다. 이게 "무엇을 받아 무엇을 보장하는가"의 실물이다.
