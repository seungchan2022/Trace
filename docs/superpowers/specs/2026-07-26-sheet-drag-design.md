# sheet-drag 설계 (MVP17 마일스톤 3)

## 결정 요약

코스 탭 바텀시트를 접고 펴는 드래그는 지금 그래버와 헤더에만 걸려 있다. 구간 리스트 위에서는 아무리 끌어도 시트가 움직이지 않는다(2026-07-19 실기기 피드백). 이 마일스톤은 **리스트가 스크롤 끝에 닿았을 때 이어지는 드래그를 시트로 넘긴다**.

규칙은 하나다.

> 리스트가 끝에 닿았는데 더 끌면, 그때부터 시트가 움직인다.

위·아래 양방향에 같은 규칙을 적용한다. 맨 위에서 아래로 당기면 시트가 작아지고, 맨 아래에서 위로 밀면 커진다. 방향마다 다른 규칙을 두지 않는다.

MVP17 킥오프 스펙(`2026-07-21-mvp17-run-history-kickoff-design.md` §8.1)은 이 마일스톤을 "설계 없음, 착수 시 브레인스토밍 선행"으로 남겨두었다. 이 문서가 그 브레인스토밍의 결과다.

## 배경 — 왜 지금까지 안 했나

백로그가 남긴 진단은 정확했다: 리스트가 `ScrollView`라 자기 팬 제스처를 이미 갖고 있어서, 시트 드래그를 그대로 얹으면 둘이 충돌한다. `tab-restructure` Task 3에서 리스트 안 스와이프가 씹히는 것을 실제로 확인했다.

여기에 더해 이 파일에는 **제스처를 잘못 붙여 시트 안 버튼이 전부 먹통이 된 회귀 이력**이 있다(2026-07-12). `sheetHeader`를 제스처로 감쌌더니 그 안의 `저장`·`전체 왕복` 버튼이 반응하지 않았고, 배경 레이어에 거는 방식으로 우회했다. 구간 행에는 버튼이 둘씩 있으므로(구간 선택, 왕복 삽입) 같은 함정이 그대로 있다.

## 동작 규칙

### 인계 조건

| 리스트 상태 | 손가락 아래로 | 손가락 위로 |
|---|---|---|
| 중간쯤 스크롤됨 | 스크롤 | 스크롤 |
| 맨 위 | **시트 축소** | 스크롤(더 갈 곳 없음 → 바운스) |
| 맨 아래 | 스크롤(더 갈 곳 없음 → 바운스) | **시트 확대** |
| 스크롤 불필요(콘텐츠가 짧음) | **시트 축소** | **시트 확대** |

콘텐츠가 뷰포트보다 짧으면 맨 위이면서 동시에 맨 아래다. 이때 리스트 전체가 그래버처럼 동작하는 것은 예외 처리가 아니라 같은 규칙에서 그대로 나온다.

**끝 도달 여부는 드래그를 시작한 시점으로 판정한다.** 손을 뗀 시점으로 보면, 리스트 중간에서 아래로 쓸어 맨 위까지 스크롤된 순간 시트까지 함께 내려간다.

### 이동 폭 — 거리에 비례

지금 드래그는 이동 거리와 무관하게 항상 한 단계만 움직인다(`steppedUp`/`steppedDown`). 풀에서 기본까지 가려면 손을 뗐다가 다시 끌어야 한다. 이 제약을 없애고 **끈 거리로 몇 단계 갈지 정한다**.

- 40pt 이하: 이동 없음
- 40pt 초과: 한 단계
- 160pt 초과: 두 단계

경계는 **초과**다 — 현재 코드가 `abs(이동량) > 40`으로 판정하고 있고, 그 동작을 그대로 유지한다. 40pt는 현재 값 그대로다. 160pt는 중간 단계 리스트 높이(≈289pt, `pageHeight × 0.4` 기준)의 절반 남짓으로, "명백히 크게 끌었다"는 의도가 분명한 거리다. 끝에서 더 못 가면 그대로 머문다.

시트 단계 모델은 기존 `SheetDetent` 3단계(기본/중간/풀)를 그대로 쓴다. 단계를 늘리거나 연속 높이로 바꾸지 않는다.

### 진입점은 늘리고 규칙은 하나로

리스트 드래그, 그래버 드래그, 헤더 드래그가 **같은 이동 규칙**을 쓴다. 이 파일에는 이미 *"탭과 드래그의 동작이 달라선 안 된다"*는 원칙이 못박혀 있다(2026-07-12, 빈 경로일 때 탭은 되는데 드래그는 안 되던 불일치를 고치며 확정). 같은 이유로 그래버 드래그도 거리 비례로 함께 바꾼다.

바뀌지 않는 것: **헤더 탭은 기본↔중간만 오간다.** 풀은 드래그로만 도달한다(2026-07-12 사용자 확정).

시트 단계 변경은 기존 단일 진입점을 계속 통과한다. 그 안에 접기 직전 스크롤 앵커를 기억하는 로직이 있어서, 리스트 드래그로 접어도 재펼침 시 위치 복원이 똑같이 동작한다.

## 구현 방향

### 제스처 공존 방식

`ScrollView`에 드래그 제스처를 **동시 인식(simultaneous)으로 얹는다.** 스크롤은 평소대로 동작하고, 새 제스처는 소유권을 뺏지 않은 채 이동량만 관찰한다.

- 최소 이동 거리를 두므로 탭에는 발동하지 않는다. 기존 버튼 회귀는 제스처로 뷰를 **감싸서** 탭까지 가로챈 경우였고, 동시 인식은 그 경로를 타지 않는다.
- 대가: 한 번의 손동작 안에서 "스크롤하다 끝에 닿아 즉시 시트로 인계"는 안 된다. 손을 떼고 다시 끌어야 한다. 어차피 손을 뗄 때 단계로 스냅하는 구조라 연속 인계가 어울리지 않는다.
- `ScrollView`·`scrollPosition`·`LazyVStack`·자동 스크롤 로직은 전부 그대로 둔다.

검토 후 기각한 대안 둘:

- **스크롤 비활성 토글** — 끝에 닿으면 스크롤을 껐다가 다시 켠다. 켜고 끄는 순간 스크롤이 끊기고, 다시 켜는 시점을 놓치면 리스트가 얼어붙는다. 상태만 늘고 얻는 게 없다.
- **`UIScrollView` 래핑** — 한 손동작 내 매끄러운 인계까지 가능하지만, 리스트 렌더링을 UIKit으로 다시 만들고 스크롤 위치 복원·최신 구간 자동 스크롤·`colorKey` 행 정체성을 전부 새로 짜야 한다. 이번 요구에 비해 대가가 지나치다.

### 판단 로직은 뷰에서 분리한다

두 가지를 순수 계산으로 빼고 테스트로 못박는다. 이 저장소가 `SheetHeightBudget`·`FabLayoutPolicy`·`SegmentPanelLogic`에 써온 방식 그대로다. 특히 이 파일의 높이 계산은 **경고 하나 없이 조용히 틀렸던 이력**이 있어(2026-07-21, 62pt가 소리 없이 사라짐) 같은 종류의 계산을 뷰 안에 두지 않는다.

1. **드래그 → 목표 단계** — 시작 단계와 세로 이동량을 받아 목표 단계를 돌려준다. 위 임계값과 클램프가 여기 있다.
2. **스크롤 끝 판정** — 콘텐츠 높이·뷰포트 높이·현재 오프셋을 받아 `(맨 위인가, 맨 아래인가)`를 돌려준다. 콘텐츠가 짧으면 둘 다 참이다.

### 되먹임 없음 — 확인 완료

이 파일은 "무언가를 재서 그 값이 다시 크기에 영향을 주는" 되먹임으로 회귀가 세 번 났던 자리다(안전영역 축소 루프, 헤더 베이스라인 흔들림, 콘텐츠 실측 기반 시트 높이). 이번에 콘텐츠 높이를 새로 재지만 여기엔 걸리지 않는다.

시트 높이는 단계·`pageHeight`·헤더 높이로만 정해지고 **콘텐츠 양과 무관**하도록 이미 만들어져 있다. 새로 재는 콘텐츠 높이는 "인계할까 말까"라는 참/거짓 판정에만 쓰이고 어떤 크기에도 먹이지 않는다. 순환이 생길 경로가 없다.

## 엣지 케이스

| 상황 | 동작 |
|---|---|
| 시트가 기본(접힘) | 리스트가 렌더되지 않음 → 리스트 인계 없음. 확대는 그래버·헤더로 |
| 드래그 시작 시 리스트가 끝에 안 닿음 | 순수 스크롤. 시트 무반응 |
| 끌던 도중 리스트가 끝에 도달 | 이번 손동작에서는 인계 안 함. 떼고 다시 끌면 인계 |
| 구간 0개 (리스트 빔) | 콘텐츠 높이 0 → 양끝 동시 참 → 리스트 영역이 그래버처럼 동작 |
| 확대로 리스트가 길어짐 | 기존 스크롤 앵커(`anchor: .center`)가 보던 행을 중앙에 유지 |
| 축소로 리스트가 사라짐 | 기존 앵커 기억 로직이 그대로 동작 → 재펼침 시 위치 복원 |
| 왕복 버튼 위에서 드래그 시작 | 최소 이동 거리를 넘는 순간 버튼 액션 취소, 드래그로 인식 (iOS 기본) |

## 범위와 비범위

### 포함

- 구간 리스트 영역에서 스크롤 끝 도달 시 양방향 시트 인계
- 드래그 이동 폭을 거리 비례로 변경 (리스트·그래버·헤더 공통)
- 드래그 판정과 스크롤 끝 판정을 순수 계산으로 분리 + 경계값 테스트
- 실기기 QA 체크리스트 작성과 결과 수용

### 제외

- **손가락 추종(연속 높이)** — 끄는 동안 시트가 실시간으로 따라오는 방식. 시트 높이를 연속 값으로 바꿔야 하고, 되먹임 회귀가 세 번 난 계산을 다시 흔든다. *트리거:* 단계 스냅만으로 뻣뻣하다는 판단이 실기기에서 서면 별도 마일스톤
- **한 손동작 내 인계** — 스크롤하다 끝에 닿는 즉시 시트로 넘어가기. `UIScrollView` 래핑이 필요. *트리거:* 떼고 다시 끄는 것이 실사용에서 거슬리면
- 시트 단계 수 변경, 헤더 탭 동작 변경
- 시트 높이 계산식 변경
- 러닝·기록 탭 (해당 시트가 없음)

## 완료 기준

1. 리스트 맨 위에서 아래로 당기면 시트가 축소되고, 맨 아래에서 위로 밀면 확대된다.
2. 리스트 중간에서 드래그하면 시트가 움직이지 **않는다**.
3. 구간 행의 선택 버튼과 왕복 버튼이 그대로 동작한다.
4. 길게 끌면 두 단계를 한 번에 이동한다.
5. 순수 로직 두 가지가 경계값 테스트로 덮여 있다.
6. 실기기 QA 6항목을 사용자가 통과 판정한다.

## 검증 전략

- **자동:** 드래그 판정·스크롤 끝 판정의 경계값 단위 테스트(문턱 직전·직후, 각 시작 단계, 양방향, 클램프). 시트 단계는 접근성으로 직접 읽을 수 없으므로 UI 테스트는 시트 요소의 **높이 변화**로 판정한다.
- **시뮬레이터:** 리스트 드래그를 합성해 단계가 바뀌는지, 버튼이 여전히 눌리는지 확인한다.
- **시뮬레이터로 확인 불가 — 미리 인정한다:** 바운스 감각과 인계가 손에 자연스럽게 잡히는지는 합성 제스처로 판정할 수 없다. `draw-gesture`에서 롱프레스-드래그 합성 한계를 스모크 통과로 뭉뚱그리지 않고 INCONCLUSIVE로 기록한 선례를 따른다.
- **실기기 QA (한 세션):**
  1. 리스트 맨 위에서 아래로 당김 → 시트 축소
  2. 리스트 맨 아래에서 위로 밀기 → 시트 확대
  3. 구간 1개일 때 리스트 아무 데나 잡고 양방향
  4. **구간 선택 버튼·왕복 버튼이 여전히 눌리는가** ← 회귀 1순위
  5. 길게 끌기 → 두 단계 한 번에 이동
  6. 리스트 중간에서 드래그 → 시트가 움직이지 **않아야** 함

4번이 가장 위험하다. 이 파일에서 실제로 났던 회귀이고, 자동 테스트로는 "버튼이 눌린다"까지만 확인되지 손가락 감각은 잡히지 않는다.
