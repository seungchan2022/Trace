# 워크플로 진행 순서 (사용자용)

> **이 문서는 규칙이 아니라 순서표다.** 규칙 원문은 `docs/agent-rules/workflow.md`에 있고,
> 여기는 "무엇을 언제 하는지"와 "어디를 보면 되는지"만 담는다. 상세를 여기 복사하지 않는다.
>
> 2026-07-30 개정 반영 · 개정 경위는 `docs/workflow-audit.md`

---

## 세션을 어떻게 나누나

```
📄 문서 세션 (모델 ↑)      💻 구현 세션 (모델 ↓)
   설계 → ce리뷰 → 계획   →    구현 → QA → 마일스톤 닫기
   ▸ 사이클 하나 끝나면 세션을 닫는다
```

**한 세션에서 다음 사이클 문서까지 이어 쓰지 않는다.** 찬 세션을 이어 쓰는 비용이
새 세션 + `trace-init`보다 크고, 컨텍스트가 크면 초점도 흐려진다.

**정비와 버그는 문서 세션이 필요 없다.** 구현 세션 하나에서 끝낸다.

---

## 1. MVP 시작 (문서 세션)

1. `/trace-init`
2. `docs/backlog.md`에서 이번 MVP에 담을 것 고르기
3. `brainstorming`으로 마일스톤 쪼개기
4. **킥오프 문서에 이 표를 넣는다**

   | 마일스톤 | 종류 | 앞 결과에 의존하나 |
   |---|---|---|
   | `<슬러그>` | 새 기능 / 작은 기능 / 정비 | 없음 / ⚠️ `<앞 마일스톤>`의 무엇 |

   - 의존 칸은 **잠정**이다. 실기기 QA가 앞 마일스톤의 처방을 뒤집으면 그때 갱신한다.
   - **킥오프 문서는 사이클 설계를 겸하지 않는다.** 마일스톤 목록과 종류만 담는다.
5. `docs/roadmap.md`에 등록

---

## 2. 마일스톤 준비 (문서 세션)

**종류에 따라 밟는 단계가 다르다.**

| 단계 | 새 기능 | 작은 기능 | 정비 | 버그 |
|---|---|---|---|---|
| 설계 문서 | ○ | ○ | ✕ | ✕ |
| `ce리뷰` | ○ | ✕ | ✕ | ✕ |
| **대상 목록·분류** | — | — | **○ 필수** | ✕ |
| 계획 문서 | ○ | ○ | 위험 갈래만 | ✕ |
| TDD · Task별 검사 | ○ | ○ | ○ | ○ |
| 실기기 QA | ○ | ○ | 조건부 면제 | 경우에 따라 |
| 최종 브랜치 검사 | ○ | ✕ | ✕ | ✕ |

- **애매하면 한 칸 무거운 쪽**을 고른다.
- 진행 중 성격이 달라지면 멈추고 상의한 뒤 올린다.
- 종류가 섞인 마일스톤은 한 사이클로 묶지 않는다.

**여기까지 하면 세션을 닫는다.**

---

## 3. 구현 (구현 세션)

1. `/trace-init` → **"지금 할 수 있는 것"이 목록으로 뜬다**

   ```
   A. 사이클 '<슬러그>' 구현        — 문서 준비됨
   B. 사이클 '<슬러그>' 목록·분류    — 정비. 설계 불필요
   ⚠️ '<슬러그>'는 아직 불가 — '<앞>'의 실기기 QA 결과 필요
   ```

   킥오프 표가 없는 예전 MVP에서는 "정보 없음"으로 알리고 기존 방식대로 간다.

2. 고른 것을 구현 — TDD → Task별 검사 → 커밋
3. **커밋할 때 계획 체크박스를 같이 담는다** (체크박스만 고치는 커밋을 만들지 않는다)

---

## 4. 마일스톤 닫기

**계획 문서의 Task가 아니라 정해진 절차다.**

1. 실기기 체크리스트를 `docs/qa/`에 직접 쓴다 (`testing.md` 템플릿)
2. 사용자에게 제시 → 결과를 한 번에 받는다
3. 결과를 가른다 — 진짜 고장은 지금, 개선은 `docs/backlog.md`
4. `docs/roadmap.md` 마일스톤 `[x]`
5. **`milestone-retro` 제안** (넘겨도 된다)

---

- `trace-study` — 학습 정리 (선택)
