# 요약

**정비 플랜의 "무엇이 깨질지" 사전 분류는 실측과 자주 어긋난다.** 두 사이클 연속으로 뒤집혔다.
분류 표를 없애자는 게 아니라 — 분류는 여전히 생략 금지다 —
**분류를 가설로 다루고, 항목을 하나씩 떼어 각각 검증하라**는 것이다.

# 사례 두 건

## ① `lint-cleanup` (MVP17, 2026-07-27)

- **분류:** 린트 경고 44건을 "의미 축약 이름이니 고치면 된다"로 묶음
- **실제:** 그중 **5건이 `Codable` 저장 JSON 키**였다. 그냥 개명했다면 사용자 기기의 러닝 기록이
  전부 해독 불가가 되고, **새로 설치한 환경에서는 증상이 없어 QA로도 못 잡혔을** 경로였다
- 원문: `docs/solutions/conventions/codable-property-rename-breaks-stored-blobs.md`

## ② `study-chunk-0-cleanup` (2026-08-04)

Task 4(Domain 프로토콜 4개의 `@MainActor` 제거)에서 플랜이 이렇게 적어뒀다:

> 깨지는 곳은 **대부분 가짜 구현체 6개**로 예상된다 — 진짜 구현체 4개는 이미 자체
> `@MainActor`를 갖고 있어 영향이 없다(실측 확인). ⚠️ `VoiceAnnouncerProtocol`은
> `async`가 아니라서 파급이 다를 수 있다.

**실제로는 정확히 반대였다:**

| 플랜 예상 | 실제 |
|---|---|
| 가짜 구현체 6개가 깨진다 | **한 곳도 안 깨짐** |
| 진짜 구현체 4개는 안전하다 | **전부 깨짐** |
| `VoiceAnnouncerProtocol`이 위험하다 | **유일하게 아무 조치 없이 통과** |

같은 Task에서 작은 것도 하나 더 뒤집혔다 — 백로그가 "호출부는 `RootView` 하나뿐"이라 했으나
실제로는 셋이었다(결론은 맞았지만 근거가 틀렸다).

# 무엇이 바로잡았나 — 항목별 분리 검증

Task 4에서 처음엔 **네 프로토콜을 한꺼번에 떼고 한 번 빌드**했다. 에러가 쏟아지자
"진짜 구현체까지 번졌으니 중단"으로 읽고 **3개를 되돌렸다**(1/4만 처리).

그 판단이 틀렸다. **프로토콜을 하나씩만 떼고 각각 빌드**하자 규칙이 드러났다 —
가르는 축은 "진짜/가짜"가 아니라 **`async` 요구사항의 유무**였고, 그걸 알고 나니
`nonisolated` 없이 **4개 전부** 처리할 수 있었다.

**비용은 빌드 4번(약 4분)이었다.** 그 4분이 "3개는 불가능"이라는 잘못된 결론을 뒤집었다.

# 그래서 어떻게 하나

1. **분류 표는 계속 만든다** (`workflow.md` 정비 경로 1항, 생략 금지). 분류가 위험을 드러낸다.
2. **다만 분류의 "무엇이 깨질까"는 가설로 취급한다.** 플랜에 확신 있게 적혀 있어도 그렇다.
3. **한 번에 하나씩 바꾸고 각각 빌드한다.** 여러 개를 한꺼번에 바꾸면 에러가 섞여
   **원인을 오독하고, 오독이 "불가능" 결론으로 굳는다.**
4. **중단 기준이 발동해도 한 번은 쪼개 본다.** "에러가 예상 밖으로 번졌다"는 신호는
   *진짜 위험*일 수도, *묶어서 본 탓*일 수도 있다. 쪼개면 구분된다.

# 왜 반복되나

정비 대상은 **코드를 읽어서 분류**한다. 그런데 이 두 사례가 걸린 곳은 **읽어서는 안 보이는
층**이었다 — ①은 프로퍼티 이름과 저장 포맷의 연결, ②는 컴파일러의 격리 추론 규칙.

**"코드를 읽어서 세운 분류"는 컴파일러·런타임이 확인해 주기 전까지 가설이다.**
