## Context

MVP17 `lint-cleanup` 마일스톤에서 서브에이전트가 파일을 편집한 직후,
SourceKit이 "타입을 찾을 수 없음" 같은 진단을 대량으로 띄우는 일이 **세 차례 반복**됐다.

실제로는 코드가 깨진 것이 아니었다. **IDE 색인이 파일 변경을 따라가지 못한 스테일 노이즈**였다.
매번 `xcodebuild build`를 독립적으로 돌려보니 컴파일은 정상이었다.

이 마일스톤은 이름 변경 13건과 저장 키 고정을 포함해 여러 파일을 연달아 손댔다.
편집 범위가 넓을수록 색인이 뒤처질 여지가 커진다.

## Guidance

**IDE 진단을 근거로 조사를 시작하기 전에, 빌드를 한 번 돌려 실제 컴파일 상태를 확인한다.**

```bash
xcodebuild build -scheme Trace -destination 'id=<시뮬레이터 UDID>' | tail -5
```

- **빌드가 성공하면** IDE 진단은 노이즈다. 무시하고 다음 단계로 간다.
- **빌드가 실패하면** 그때부터 진짜 문제다. 진단 내용이 유효하다.

판별 신호 — 아래에 해당하면 색인 지연을 먼저 의심한다.

| 신호 | 왜 |
|---|---|
| 방금 편집하지 않은 파일에서도 오류가 난다 | 색인 전체가 뒤처진 상태 |
| 오류 수가 비정상적으로 많다 (수십 건) | 실제 실수라면 이렇게 광범위하게 퍼지지 않는다 |
| 내용이 "타입/심볼을 찾을 수 없음"에 집중된다 | 색인이 새 선언을 아직 못 읽은 전형적 모습 |
| 방금 여러 파일을 연달아 편집했다 | 색인이 따라잡을 시간이 없었다 |

## Why This Matters

**두 방향으로 시간을 잃는다.**

1. **없는 문제를 조사한다.** 진단을 믿고 원인을 찾기 시작하면, 정상인 코드를 몇십 분씩 뒤진다.
2. **반대로, 진짜 문제를 노이즈로 치부한다.** "또 색인 문제겠지"라고 넘기면 실제 컴파일
   오류를 놓친다.

**빌드 한 번이 두 방향 모두를 막는다.** 판단이 아니라 실측이기 때문이다.

그리고 이건 서브에이전트로 작업할 때 더 자주 만난다. 사람이 파일 하나를 고칠 때와 달리,
서브에이전트는 한 태스크에서 여러 파일을 연달아 바꾼다.

## When to Apply

- 서브에이전트가 편집을 마치고 보고한 직후 (컨트롤러 쪽 검증 단계)
- 여러 파일을 일괄 변경한 뒤 (이름 정리, 일괄 리팩터링 등)
- IDE 진단과 서브에이전트 보고가 어긋날 때

해당 없는 경우: 파일 하나를 손댄 뒤 그 파일에서만 오류가 나는 경우 — 대개 진짜 오류다.

## Examples

**하지 말 것 — 진단을 믿고 조사 시작**

```
서브에이전트: Task 2 완료. 빌드 성공, 테스트 통과.
IDE:         Cannot find type 'RunSplit' in scope  (그 외 30여 건)
컨트롤러:     (타입 선언을 찾아 파일들을 뒤지기 시작)   ← 없는 문제를 조사
```

**할 것 — 빌드로 먼저 실측**

```
서브에이전트: Task 2 완료. 빌드 성공, 테스트 통과.
IDE:         Cannot find type 'RunSplit' in scope  (그 외 30여 건)
컨트롤러:     xcodebuild build → BUILD SUCCEEDED    ← 노이즈 확인
             (다음 단계로 진행)
```

MVP17 `lint-cleanup`은 이 순서를 전 태스크에 일관되게 적용했고, 세 번 모두 노이즈로 판별했다.
